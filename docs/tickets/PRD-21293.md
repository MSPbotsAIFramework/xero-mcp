## Product design

### Goals / Non-goals

**Goals** (this ticket):

- G1: An agent can list and read a Xero bank account's own transactions (money spent or received that is not an invoice/bill payment — e.g. bank fees, interest, ad-hoc deposits), including whether each one is already reconciled in Xero.
- G2: An agent can record a bank-account spend or receive transaction on the user's explicit request, so the books stay accurate ahead of reconciliation.
- G3: An agent can list, read, and record a transfer of funds between two of the organisation's bank accounts.
- G4: These new tools are discoverable the same way as the existing five areas, via `xero_navigate` / `xero_back`.

**Non-goals**:

- NG1: Automatically matching an imported bank statement line to an existing transaction — the action behind Xero's "Reconcile" screen. See Open Questions, this is a stated assumption, not a gap left for later in this design.
- NG2: Importing bank feeds/statements from a bank. Same reason as NG1.
- NG3: Editing or deleting an existing bank transaction or transfer. No existing tool in this repo supports editing a written record either (only `xero_invoices_update_status` changes status, and only for invoices); keeping the new tools to list/get/create matches the repo's existing minimal-footprint pattern.
- NG4: Any UI work. This ticket is entirely inside the `xero-mcp` server; the Agent platform's connector framework and docs.mspbots.ai connector page are unaffected by this design (the connector wiki page itself is still updated by the review leg, mcp-track.md § 4.5).

### Why NG1/NG2 is the right reading of "bank reconciliation" here

Xero's public Accounting API (2.0) — the API this server already uses exclusively — exposes `BankTransactions` (spend/receive money entries, with a read-only `IsReconciled` flag) and `BankTransfers` (moves between bank accounts). It does **not** expose an endpoint that performs the "match a statement line to a transaction" action a human does on Xero's Reconcile screen; that requires the separate Bank Feeds API, which needs Xero partner/certification approval and is a different integration shape entirely (a feed provider, not a tool an agent calls on demand). Building G1–G3 is the full extent of "bank reconciliation" reachable from the API this connector is built on.

### Acceptance criteria AC1..AC10

- **AC1**: Given valid credentials, When the agent lists bank transactions (optionally filtered by bank account and/or status), Then it gets spend/receive transactions newest-first, 100 per page, each showing date, type, amount, reference, bank account, and whether it is reconciled.
- **AC2**: Given a bank transaction id, When the agent asks for it by id, Then it gets the full transaction (line items, tax, totals, reconciled flag).
- **AC3**: Given a bank account id and at least one line item, When the agent is explicitly asked to record money spent from that account, Then a SPEND transaction is created in Xero against that account.
- **AC4**: Given a bank account id and at least one line item, When the agent is explicitly asked to record money received into that account, Then a RECEIVE transaction is created in Xero against that account.
- **AC5**: Given valid credentials, When the agent lists bank transfers, Then it gets transfers newest-first, 100 per page, each showing the source and destination accounts, amount, and date.
- **AC6**: Given a bank transfer id, When the agent asks for it by id, Then it gets the full transfer (both accounts, amount, date, the two linked bank transaction ids).
- **AC7**: Given two different bank account ids and an amount, When the agent is explicitly asked to transfer funds between them, Then a transfer is created moving funds from the source to the destination account.
- **AC8**: Given the agent calls `xero_navigate("bank")` or `xero_back`, Then the response names the new bank-transactions/bank-transfers tools and a one-line summary of what they do, the same way the other five areas already do.
- **AC9**: Given a bank account id, contact id, or transaction id that is missing, not a UUID, or does not exist, When any new tool is called with it, Then the response is the server's standard structured error envelope (`invalid_argument` or `not_found`), never a raw exception — matching every existing tool.
- **AC10 (multi-tenant / isolation)**: Given two different callers send two different `X-Xero-Tenant-Id` values, When each calls any new tool, Then each only ever sees and writes their own organisation's data — the new tools carry no new state and reuse the same per-request credential plumbing as every existing tool (`src/xero_mcp/server.py:41-44,83-117`), so there is no new cross-tenant surface to introduce.

### Open questions

- [已假设] "Bank reconciliation" is implemented as G1–G3 above (view bank-account transactions and their reconciled status, record spend/receive entries, record transfers) rather than automated statement-line matching, because the latter is not reachable through the Accounting API this connector already uses and would require a different kind of integration (Bank Feeds partner API). **Not blocking**: this is the only capability reachable with the existing API and credential model, so there is no alternative reading that changes the design. If product actually wants bank-feed matching, that is a materially different, much larger integration and should come back as its own ticket with the Bank Feeds partnership question answered first.
- [不阻塞] The ticket does not say which bank-transaction types an agent should be allowed to create. This design scopes `xero_bank_transactions_create` to `SPEND` and `RECEIVE` only (the two types a person would ask for in plain language) and excludes the four Xero-internal variants (`*-OVERPAYMENT`, `*-PREPAYMENT`) that Xero itself generates as a side effect of other actions — default by omission, can be widened later if a concrete need shows up.

## Tech design

### Conclusion

Add one new tool module, `src/xero_mcp/tools/bank.py`, registering 6 tools (`xero_bank_transactions_{list,get,create}`, `xero_bank_transfers_{list,get,create}`) against the Xero `BankTransactions` / `BankTransfers` endpoints, following the exact list/get/create shape `payments.py` already uses against the same API family. Wire it into `xero_navigate`/`xero_back` and `create_mcp_server`. No new dependency, no new credential path, no schema/DB (this server has none) — it is an additive tool surface on the same API client.

### Option analysis

No alternative API or vendor SDK: the repo already standardises on calling the Xero Accounting API 2.0 directly via `httpx` through `XeroClient` (`api_client.py`), and `BankTransactions`/`BankTransfers` are resources of that same API — using anything else (a different SDK, a different API version) would introduce a second HTTP calling convention into a single-purpose connector for no benefit.

One real choice: how to group the 6 new tools.

| Option | Shape | Pros | Cost | Verdict |
|---|---|---|---|---|
| A: one module `bank.py`, one new `xero_navigate` domain `"bank"` covering both resources | 6 tools, 1 domain | Mirrors `reports.py`, which already bundles 4 distinct report endpoints under one `"reports"` domain; keeps the domain list short and matches how a bookkeeper talks about "the bank" as one area | Domain summary string has to cover two sub-resources in one line | **Chosen** |
| B: two modules/domains, `bank_transactions.py` + `bank_transfers.py` | 6 tools, 2 domains | Slightly more granular `xero_navigate` output | Grows the domain list from 5 to 7 for a pair of resources a user experiences as one concept ("moving money through the bank"); no existing module is this narrowly split | Rejected — splits what the repo's own naming convention (`reports.py`) says should stay together |

### Data & API contract

Base URL and auth are unchanged (`https://api.xero.com/api.xro/2.0/...`, `Authorization: Bearer <token>`, `xero-tenant-id: <tenant>`, `api_client.py:134-144`).

**`xero_bank_transactions_list`** → `GET BankTransactions?page=&where=&order=BankTransactionID` style, mirroring `xero_invoices_list` (`invoices.py:68-81`):

```
GET /BankTransactions?page=1&where=BankAccount.AccountID==guid("...") AND Status=="AUTHORISED"&order=Date DESC
→ 200 {"BankTransactions": [
  {"BankTransactionID": "...", "Type": "SPEND", "Status": "AUTHORISED", "IsReconciled": false,
   "Date": "2026-10-20T00:00:00Z", "Reference": "Bank fee", "Total": 12.50,
   "BankAccount": {"AccountID": "...", "Code": "090", "Name": "Business Checking"},
   "LineItems": [...] }
]}
```
Mapped through `page_result("BankTransactions", ...)` exactly like `xero_invoices_list` / `xero_payments_list`.

**`xero_bank_transactions_get`** → `GET /BankTransactions/{id}` → `first(..., "BankTransactions")`, same as `xero_payments_get`.

**`xero_bank_transactions_create`** → `PUT /BankTransactions` body:

```json
{"BankTransactions": [{
  "Type": "SPEND",
  "BankAccount": {"AccountID": "<guid>"},
  "LineItems": [{"Description": "Bank fee", "Quantity": 1, "UnitAmount": 12.50, "AccountCode": "404"}],
  "Contact": {"ContactID": "<guid>"},
  "Date": "2026-10-20",
  "Reference": "Monthly fee"
}]}
```
`Type` is restricted to `SPEND`/`RECEIVE` (AC3/AC4; see Open Questions). `ContactID` is optional — Xero allows a bank transaction with no contact. Response mapped through `write_result(..., "BankTransactions")`, which already surfaces `ValidationErrors` the same way `xero_invoices_create` does (`_common.py:134-141`).

**`xero_bank_transfers_list`** → `GET /BankTransfers?page=` (this endpoint has no `where`/`order` support in Xero's API — newest-first is Xero's default order) → `page_result("BankTransfers", ...)`.

**`xero_bank_transfers_get`** → `GET /BankTransfers/{id}` → `first(..., "BankTransfers")`.

**`xero_bank_transfers_create`** → `PUT /BankTransfers` body:

```json
{"BankTransfers": [{
  "FromBankAccount": {"AccountID": "<guid>"},
  "ToBankAccount": {"AccountID": "<guid>"},
  "Amount": 500.00,
  "Date": "2026-10-20"
}]}
```
Response includes `BankTransferID`, `FromBankTransactionID`, `ToBankTransactionID` (the two linked `BankTransactions` Xero creates on either side of the transfer) — mapped through `write_result(..., "BankTransfers")`.

**Errors**: identical envelope to every existing tool (`{"error": {"code", "message", "retryable"}}`, `_json.py` via `XeroError.to_envelope()` / `error_envelope()`); no new error code needed — `invalid_argument` (bad guid, Xero 400), `not_found` (Xero 404), `upstream_error` (5xx/network) already cover this resource family.

**Backward compatibility**: purely additive — 6 new tool names, no change to any existing tool's name, parameters, or response shape. Nothing for an existing caller to break against.

### Key flow / sequence

```
Agent -> xero_bank_transactions_list(BankAccountID?, Type?, Status?, page?)
      -> XeroClient.get("BankTransactions", {page, where, order})
      -> Xero Accounting API
      <- {BankTransactions: [...]}
      -> page_result(...) -> JSON string -> Agent

Agent -> xero_bank_transactions_create(Type, BankAccountID, LineItems, ...)   # only on explicit request
      -> XeroClient.put("BankTransactions", body)        # Idempotency-Key auto-attached (api_client.py:142-144)
      -> Xero Accounting API
      <- {BankTransactions: [{...created record, ValidationErrors?}]}
      -> write_result(...) -> JSON string -> Agent
```
`xero_bank_transfers_*` follows the identical shape against `/BankTransfers`.

### Non-functional

- **Idempotency & concurrency**: inherited for free — every non-GET request already gets a fresh `Idempotency-Key` header from `api_client.py:142-144` regardless of resource, so a retried `xero_bank_transactions_create`/`xero_bank_transfers_create` cannot create a duplicate record. No per-tool change needed.
- **Performance**: same 100-record page model as every existing list tool (`PAGE_SIZE = 100`, `_common.py:45`); Xero's 60/min, 5,000/day rate limit is already handled generically by `api_client.py`'s retry/backoff (`:165-193`). No new hot path.
- **Security**: no new credential surface — the new tools read the same per-request `X-Xero-Access-Token`/`X-Xero-Tenant-Id` the middleware already extracts (`server.py:83-117`); nothing is stored, nothing is logged (the existing `logger.info` calls in `run_tool`/`request` never include the token or body, `_common.py:160-168`, `api_client.py:160-163`).
- **Multi-tenant isolation**: unchanged mechanism — the tenant id travels on the request header into a context-local `XeroCredentials`, never shared state (`server.py:41-44`); see AC10.
- **Observability**: the generic `run_tool()` wrapper (`_common.py:144-171`) already logs `tool=<name> outcome=... ms=...` for any tool registered through it — the 6 new tools get this automatically, no new logging code required.

No feature flag mechanism exists in this stateless MCP server — a deployed version's tools are simply what `tools/list` returns. Rollback is reverting the merge commit and republishing, same as any other change to this repo; no data migration exists to roll back (no DB, no schema). Single repo, no cross-repo dependency — **release order: n/a (single MCP repo, purely additive change, no platform-side coupling)**.
